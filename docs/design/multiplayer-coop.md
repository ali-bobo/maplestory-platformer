# 雙人合作連線設計（草案）

狀態：設計草案，尚未實作。評估背景見專案資料夾 `plans/multiplayer-assessment-2026-10-20.md`。

## 1. 範圍

**要做的（MVP）**：兩位玩家用房號連線，一起打「副本」和「Boss 房」。

**不做的**：大地圖同步、整隊換圖、交易、聊天、三人以上、跨裝置存檔、排行榜。大地圖照舊單人遊玩。

選這個範圍的原因：副本（`DungeonScene`）和 Boss 房（`BossScene`）都是「進場、打完、結算、回城」的封閉流程，不需要處理換圖、NPC、任務、商店的同步。

## 2. 核心架構：「各自控制自己的角色，怪物由房主模擬」

```
房主（Host）                                 客人（Guest）
┌──────────────────────────┐               ┌──────────────────────────┐
│ 自己的 Player（照舊）     │  玩家狀態 15Hz │ 自己的 Player（照舊）     │
│ 客人的替身 RemotePlayer   │◀──────────────│                          │
│ 怪物 / Boss AI（照舊執行）│               │ 怪物「木偶」（不跑 AI）    │
│ 怪物 HP、生死、波次、計時 │──────────────▶│ 依快照內插畫面            │
│                          │  怪物快照 15Hz │ 房主的替身 RemotePlayer   │
│                          │  + 事件（可靠）│                          │
└──────────────────────────┘               └──────────────────────────┘
```

| 東西 | 誰說了算 | 理由 |
|---|---|---|
| 自己角色的移動、跳躍、技能施放、HP、MP、冷卻 | 各自的裝置 | 手感零延遲；現有 `Player.js` 幾乎不用改 |
| 怪物位置、AI、出招、HP、死亡、掉落 | 房主 | 只有一份模擬，不會分歧；`Math.random`、變動 delta 都不用處理 |
| 客人打怪是否命中 | 客人本機判定，送「命中申報」給房主 | 打擊感不受延遲影響；房主做上限檢查 |
| 怪物打客人是否命中 | 房主判定，送「受傷事件」給客人 | 怪物 AI 在房主那邊跑 |
| 波次、計時、勝敗 | 房主 | 副本流程本來就在 `DungeonScene` |
| 獎勵、存檔 | 各自的裝置 | 收到結算事件後各自呼叫 `_grantRewards`、`saveGame` |

這個模型不是防作弊的。朋友之間連線可以接受；若以後要排行榜，成績不能以客戶端為準。

## 3. 連線層

- **傳輸**：WebRTC DataChannel，開兩條 channel：
  - `state`：不可靠、不排序（`ordered:false, maxRetransmits:0`），放高頻位置快照，掉了就用下一筆。
  - `event`：可靠、排序，放出招、受傷、命中、波次、結算。
- **配對（signaling）**：首選 PeerJS（npm `peerjs`）＋其公用配對伺服器，免架站。房主開房得到 6 碼房號，客人輸入房號連入。備案：Firebase Realtime Database 免費方案。
- **NAT 穿透**：Google 公用 STUN；手機網路需要 TURN 中繼，需申請一個有免費額度的 TURN 服務（金鑰問題見第 9 節）。
- **網站仍是 GitHub Pages 靜態站**，不需要自己的伺服器。

## 4. 訊息格式（`src/net/protocol.js`）

全部是 JSON（先求好除錯，流量很小：每秒約 15 筆 × 1 KB 以內）。每筆帶 `t`（類型）。

| 類型 | 方向 | 頻道 | 內容 |
|---|---|---|---|
| `hello` | 雙向 | event | 遊戲版本（`dist/version.json`）、職業、等級、名稱 |
| `start` | 房主→客 | event | 副本 id、亂數種子、人數係數 |
| `ps` | 雙向 | state | 玩家快照：x, y, vx, vy, 貼圖 key, 面向, HP 比例, 狀態旗標 |
| `ms` | 房主→客 | state | 怪物快照陣列：id, x, y, 貼圖 key, 面向, HP |
| `spawn` / `die` | 房主→客 | event | 怪物出生（id、怪物種類、位置）/ 死亡 |
| `atk` | 房主→客 | event | 怪物開始出招：怪物 id、招式 id、瞄準點（客人端播蓄力動作與特效） |
| `hurt` | 房主→客 | event | 客人被打：傷害、來源 x、擊退力 |
| `hit` | 客→房主 | event | 命中申報：怪物 id、傷害、是否爆擊、擊退 |
| `fx` | 雙向 | event | 對方施放技能的純視覺特效（技能 id、位置、方向） |
| `wave` / `result` | 房主→客 | event | 波次、勝敗與獎勵數字 |
| `bye` | 雙向 | event | 主動離開 |

## 5. 程式要改的地方

| 檔案 | 改動 |
|---|---|
| `src/net/transport.js`（新） | 包 PeerJS：開房、加入、兩條 channel、斷線偵測（5 秒沒收到 `ps` 視為斷線） |
| `src/net/loopback.js`（新） | 記憶體版傳輸，給單元測試和 e2e 用（同一頁兩個實例互傳） |
| `src/net/protocol.js`（新） | 訊息編碼、解碼、欄位驗證（純邏輯，有單元測試） |
| `src/net/interp.js`（新） | 快照緩衝與內插（延後 100 ms 播放；純邏輯，有單元測試） |
| `src/net/session.js`（新） | 連線狀態機：大廳 → 準備 → 遊戲中 → 結算；版本不符直接拒絕 |
| `src/entities/RemotePlayer.js`（新） | 隊友替身：只有貼圖、名字、血條、物理身體（給怪物 AI 當目標），不讀鍵盤 |
| `src/entities/Monster.js`、`monsterAI.js` | `update(player)` 改成 `update(targets)`：選最近或仇恨最高的活著的玩家；範圍招對每個玩家各判一次；打到 RemotePlayer 時改送 `hurt` 而不是扣本機 HP |
| 同上（客人端） | 新增「木偶模式」：關掉 AI 與物理，位置來自內插，收到 `atk` 時播現有的蓄力動作 |
| `src/entities/Skill.js`、`JobSkills.js` | 命中怪物時，客人端改為送 `hit`；`hitStop()` 在連線模式只放慢本機畫面，不放慢房主的物理世界 |
| `src/scenes/BaseMapScene.js` | 畫面外剔除、撿東西改用「最近的玩家」；加 `this.players` 陣列 |
| `src/scenes/CoopDungeonScene.js`（新） | 繼承 `DungeonScene`：房主跑波次，客人只聽事件；結算各自發獎勵 |
| `src/scenes/CoopBossScene.js`（新） | 繼承 `BossScene`：Boss 血量依人數放大；Boss 輪流或依仇恨換目標 |
| `src/scenes/MenuScene.js` + 新大廳 UI | 主選單加「雙人合作」：開房（顯示房號）、加入（輸入房號）、選副本 |
| `src/scenes/UIScene.js` | 隊友血條與名字、連線狀態（延遲 ms）、斷線提示 |
| `src/engine/difficulty.js` | 新增人數係數（第 6 節） |
| `sw.js` | 不快取 PeerJS 的連線請求；離線時「雙人合作」按鈕顯示需要網路 |

單人模式的程式路徑保持不變：`this.players` 只有一個人時，行為與現在完全一樣。

## 6. 數值（2 人起始值，要實測再調）

- 怪物與 Boss 血量 ×1.75（最終 Boss 32000 → 約 56000）。
- 怪物傷害不變；Boss 每階段多一個範圍招，並在兩人之間換目標。
- 副本經驗與金幣：每人拿單人獎勵的 70%。
- 掉落：各自獨立，掉在自己畫面、只有自己撿得到。
- 倒地：HP 歸零先倒地 15 秒，隊友站旁邊 3 秒可救起（回 30% HP）；兩人都倒地才算失敗。
- 每日進入次數各自計算；客人等級要符合副本的 `minLevel`。

## 7. 斷線與異常

- 房主離開：客人看到「房主已離開」，直接回城，不扣經驗、不算一次進入次數。
- 客人離開：房主繼續單人打，怪物血量依剩餘人數調回去。
- iPhone 切到背景：5 秒沒有資料視為斷線（Safari 背景會停掉頁面）。
- 版本不同（其中一人快取舊版）：`hello` 比對失敗，提示「請重新整理頁面」。

## 8. 測試

- 單元測試：`protocol`、`interp`、人數係數、目標選擇（純函式，接 `test/run.js`）。
- e2e：一個瀏覽器開兩個頁面，用 `loopback` 傳輸互連，跑一場史萊姆洞窟：雙方都看到對方移動、怪物被雙方打死、結算雙方都拿到獎勵。這可以進 CI。
- 真實網路（無法自動化）：手動清單，兩台手機各在 Wi-Fi 與 4G/5G 下連線，記錄延遲與是否連得上。

## 9. 待 sam 決定

1. **配對服務**：PeerJS 公用伺服器（免設定，但不保證穩定）或 Firebase（要建一個免費專案）。建議先用 PeerJS 做原型。
2. **TURN 中繼**：手機網路需要。免費額度的 TURN 帳號需要 sam 自己申請；金鑰會出現在前端程式裡（靜態站沒辦法藏），所以要選有用量上限的方案。
3. **第一個開放的副本**：建議史萊姆洞窟（最簡單、Lv1 就能進）。
4. **新增依賴**：`peerjs` 套件。

## 10. 分階段

| 階段 | 內容 | 完成的標準 |
|---|---|---|
| P0 原型 | transport + loopback + 主選單開房 / 加入 + 晨曦鎮裡看到對方角色走動 | 兩支手機實際連上，看得到對方移動，量出延遲 |
| P1 合作副本 | 怪物木偶、命中申報、受傷事件、波次與結算、人數係數 | 兩人通關史萊姆洞窟，雙方都拿到獎勵；e2e 進 CI |
| P2 合作 Boss | Boss 換目標、倒地救援、隊友 HUD | 兩人打完最終 Boss |
| P3 打磨 | 表情、延遲顯示、斷線重連 | — |

P0 結束時再評估一次：如果手機連線率或延遲不能接受，就停在這裡，不繼續投入。
