# Design: Stage Monster Crop Rollout

## Context
目前專案已完成一批 runtime 怪物圖片接線，但仍存在三個高風險點。第一，來源怪物圖經拆分後，沒有留下足夠明確的「這一張切出了哪些 runtime png、它們屬於哪張地圖」的中介真相。第二，部分怪物被分配到多張地圖，當前配置更像是先讓場景有怪可打，而不是完成主題化整理。第三，前一次嘗試把怪物與平台整理一起做，導致視覺、碰撞與素材命名三種變因同時移動，失敗時難以定位根因。

這次 change 將根因優先視為「拆圖流程與批次邊界不清」，所以先建立怪物拆分的 Batch A，再把剩餘工作留給 Batch B。森林看台延伸、裁短與碰撞修正屬於另一條風險線，雖然需求已確認存在，但不與本批次混做。

## Goals
- 建立可重複執行的怪物拆分流程，讓每次只處理一張來源圖或一組同源怪物。
- 先完成 Batch A 的規格與任務拆解，讓後續實作可以逐步接線而不再全量改動。
- 在 Batch A 就明確要求地圖歸屬唯一化，避免同一批整理後的怪物同時掛在多張地圖。
- 要求已完成的 Batch A 怪物最終能出現在自己的地圖測試中。

## Non-Goals
- 本 change 不在本輪直接處理森林看台的 renderHeight、裁短策略或碰撞體修正。
- 本 change 不要求一次完成所有候選怪物的裁切、命名與綁定。
- 本 change 不直接刪除現有 runtime 怪物圖，也不在此時重寫整個 preload 系統。

## Batch Structure

### Batch A
- 選定第一張來源怪物圖，或一組已知同源且容易驗證的怪物集合。
- 為該批建立來源對照、切圖命名規則、地圖歸屬與地圖測試清單。
- 只讓本批怪物出現在其指定地圖，不追求一次覆蓋所有地圖。
- 完成後驗證：圖片檔、命名、monster id、spriteKey、mapData.monsters 與地圖測試結果可以互相追溯。

### Batch B
- 承接 Batch A 的命名與驗證模板，處理剩餘候選怪物與跨地圖重複配置。
- 補齊尚未整理的來源怪物圖、剩餘地圖主題化分配與 catalog 更新。
- 若 Batch A 證明拆圖流程本身仍不穩，Batch B 不得開始，必須先回頭修正流程。

## Decisions

1. 以批次導入取代全量導入。
   理由：使用者已明確指出前次失敗與拆圖流程有關。若仍一次處理全部怪物，失敗時會再次無法定位是切圖、命名、分類還是地圖綁定出錯。

2. Batch A 只接受單一來源圖或單一同源群組。
   理由：這能確保每次作業的輸入邊界固定，並讓實作後的 png、monster id 與地圖歸屬可以逐筆核對。

3. 怪物地圖歸屬在 Batch A 就開始唯一化。
   理由：使用者要求整理後的怪物只出現在自己的地圖中。這不能等到所有怪物都做完才處理，否則第一批成果依然會保留跨地圖重複。

4. 地圖測試屬於怪物拆分完成定義的一部分。
   理由：若只產出 png 與命名，仍無法證明拆分流程真的穩定。必須至少能在對應地圖生成，才算完成一批。

5. 森林看台問題延後到另一批處理。
   理由：看台問題涉及平台圖裁切、顯示比例與碰撞策略；把它和怪物拆分混在同一批會再次引入多重變因。

## Risks / Trade-offs
- 若 Batch A 選到過於複雜的來源圖，仍可能讓第一批作業過大。緩解方式是強制限制為一張來源圖，必要時只挑其中 2 到 3 個最容易辨識的怪物先驗證。
- 若現有 monsters.js 的棲地設計與目前地圖配置不一致，第一批可能需要先做最小幅度的地圖名單清理。這是可接受的，但應僅限於本批怪物。
- 若 runtime png 現況與來源圖已無法完全回推，Batch A 必須先補來源對照表，再做後續接線，避免繼續在模糊真相上施工。

## Validation Approach
- 驗證 1：本批來源圖中的每個新或已整理怪物，都能對回單一來源圖區塊與單一輸出檔名。
- 驗證 2：本批怪物的 monster id、spriteKey 與 asset catalog 條目能一一對上。
- 驗證 3：本批怪物只出現在自己的目標地圖測試中，不再同時掛在其他地圖。
- 驗證 4：若本批驗證過程中再次出現無法判定是切圖還是接線出錯，必須回寫 tasks 與 design，禁止直接擴到 Batch B。
